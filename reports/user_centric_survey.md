# 以使用者為中心的關係建模：文獻整理

問題：預測目標是使用者，其他表（PR、issue、留言、review、push、repo）都是使用者做過或接觸過的事物。這種以人為主節點的關聯資料，文獻上怎麼建模？哪些做法可以加到我們的模型？

資料來源標記：【庫】來自本機論文庫的 L1 筆記，只讀了筆記與摘要段，結果表未核對。【記憶】來自我對文獻的記憶，未在庫中核對，寫報告前需要查原文。

## 一、已經在做的：以使用者為種子的關聯圖

- 【庫】Relational Deep Learning 的做法（RelGNN、RelGT、Relational Transformer 都沿用）：每筆資料列是節點，主外鍵是邊。指定目標實體（這裡是使用者）和預測時間，只取該時間前可見的鄰居子圖，經欄位編碼和 GNN 輸出實體表示。我們的 RelBench 編碼器就是這個框架，使用者本來就是種子。
- 所以「人當主節點」不是新做法，是現有做法。可以改進的是子圖怎麼組織、事件怎麼聚合、使用者自己的時序怎麼建模。

## 二、可以加強的方向

| 方向 | 文獻做法 | 對應我們的缺口 | 成本 |
|---|---|---|---|
| A. 沿多外鍵中介表的複合訊息 | 【庫】RelGNN：把 `來源→中介→目的` 當一條原子路徑一次聚合，避免經過中介節點反覆混入無關訊息 | 已試，11/8 低 3 個百分點（35.89 對 39.06）。推測原因：我們的圖中介節點（push、review）是使用者自己的事件，本身帶時間與屬性，複合化丟掉細節。 | 已完成 |
| B. 把節點資訊整理成 token（類型、hop、時間、結構） | 【庫】RelGT：每個節點 token 編入特徵、節點類型、到目標的 hop 距離、時間、局部結構；局部注意力加上可學習的全域中心向量 | 我們的 SAGE 只靠逐層平均／加總，無法區分「同一個 repo 的近期 PR」與「一個月前的 push」。 | 中（需接 RelGT 程式） |
| C. 使用者歷史的序列模型 | 【記憶】序列推薦（GRU4Rec、SASRec）把使用者的事件當序列，用 RNN／Transformer 建模間隔與順序；時間間隔可作為輸入 | 我們的 GRU 只在「預測的七天」展開，輸入是圖聚合後的單一向量，歷史本身沒有序列編碼。可以對每位使用者最近 N 筆事件（類型、距今時間、對象 repo）做序列編碼，再與圖向量合併。 | 低到中 |
| D. 使用者記憶狀態（連續時間動態圖） | 【記憶】JODIE、TGN、TGAT：每個節點維護隨事件更新的記憶向量，用時間編碼處理事件間隔 | 對「近期活動」的連續建模，和我們的日切點加 GRU 是近似作法，但更新是逐事件。 | 高 |
| E. 協作者與共現關係（元路徑） | 【記憶】HAN、metapath2vec：沿 `user–repo–user`、`user–PR–reviewer` 等元路徑聚合，人與人之間直接相連 | 目前使用者之間靠 3 hop 才連得到；可顯式加「共用 repo 的其他使用者近期活動量」這類特徵。我們前面做過 repo 熱度特徵，GBDT 沒有提升。 | 低 |
| F. 異質圖注意力 | 【記憶】HGT、R-GCN：每種關係有獨立參數，注意力依節點與邊類型 | 與我們目前的 per-relation SAGE 類似，預期增益小。RelGT 的比較顯示 HGT 是 RDL 的標準基線。【庫】 | 中 |
| G. 手工特徵與圖表示合併 | 【記憶】RDL 的常見強基線是表格 GBDT；混合模型把使用者自己的統計特徵（近 1/7/28 天各類計數、距上次活動時間）接到圖向量後面 | 我們的 GBDT 在 11/8 輸給 GNN 3.8 點，但在 11/1、10/25 贏或平手，兩種資訊互補的可能性高。 | 低 |
| H. 把使用者當檢索 key（無使用者向量） | 【庫】AlphaFree 的命題是不學使用者 ID 向量，改用歷史互動推得表示 | 與我們「冷啟動共用節點、不使用 ID」的做法一致，可引為設計依據。 | 低（引用） |

## 三、建議在 Q2／Q3 報告中可寫的重點

- 說明「使用者為主節點、其他表為副節點」就是 RDL 的實體預測設定，並且說明我們如何用時間鄰居取樣、冷啟動共用種子來實作。
- 改進實驗的優先順序：C（歷史序列編碼）和 G（手工統計接圖向量）成本最低，也直接針對 Q3 的時間建模；B（RelGT 式 token）最貼近 Q2 的關係建模。
- 要誠實呈現：A（RelGNN）、owner／org 邊已試過未提升。
